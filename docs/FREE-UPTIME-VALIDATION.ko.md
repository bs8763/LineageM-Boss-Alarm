# 무료 운영 개선 검증 — 2026-10-29

이 변경은 `feat/free-uptime-db-discord-20261029`에서만 준비했다. 기준은 운영 main `0600ee06b1ae8e3e94000d5842e226ae1009fa2e`다. GitHub main 병합, 운영 Render 배포/환경변수 변경, 운영 PostgreSQL 접근/수정, 기존 보탐봇 1호 및 검증 봇 변경은 수행하지 않았다. 실제 운영 봇 토큰을 테스트 프로세스에 넣지 않았다. 외부 모니터링도 등록하지 않았다. APK 코드/서명/파일은 변경하지 않았다.

## 변경한 동작

- PostgreSQL에서 확정된 상태만 메모리에 복사한다. 기본 최대 보관 시간은 10분이며 시작 시 다시 읽는다. DB 읽기와 변경은 같은 순서 큐에서 처리해, 늦게 끝난 읽기가 새로운 컷/멍 기록을 덮어쓰지 않는다.
- 30초 타이머는 메모리 상태로 알림 시각을 판단한다. 아직 기록되지 않은 10분 전/5분 전/출현 알림 또는 출현 후 30분 자동 넘김이 실제로 필요할 때만 DB 트랜잭션을 실행한다. 알림 시각을 10분 단위로 미루는 변경이 아니다.
- 컷/멍/예약/복구/초기화는 기존과 동일하게 최신 DB 행을 잠그고 즉시 저장한다. COMMIT이 끝난 뒤에만 캐시를 바꾸며 실패는 성공으로 반환하지 않는다. 기존 이력과 변경 전 백업 규칙도 유지한다.
- 빈 Discord 알림 대기열은 DB 트랜잭션을 열지 않는다. 대기열에 항목이 있을 때는 기존 행 잠금·전송·커밋 순서를 유지한다.
- 화면의 보스/이력 반복 조회는 캐시를 공유한다. 명시적인 관리자 백업 및 Discord 명령 조회는 최신 DB를 읽는다.
- `/healthz`: DB 조회 없는 서버 생존 확인. `/readyz`: 최대 10분 전 검증 결과와 `lastVerifiedAt`, `maxStalenessMs`를 반환한다. 즉시 실시간 DB 연결 성공을 보장하는 응답으로 해석하면 안 된다. 캐시 만료 시 갱신 실패는 503이다.
- `/botz`: DB 조회 없이 Discord `ready`, 연결 단계, 마지막 연결 성공 시각, 제한된 오류 코드만 제공한다. 봇이 설정돼 있으나 연결되지 않았으면 503이다. 토큰/서버/사용자 ID/비밀번호는 반환하지 않는다.
- Discord 일시 로그인 실패는 약 1초부터 최대 60초까지 지연과 jitter를 두고 재시도한다. 60초 동안 완료되지 않은 로그인도 재시도한다. 잘못된 토큰/금지된 intent처럼 설정 수정이 필요한 오류는 무한 재시도하지 않고 `blocked`로 구분한다.
- 정상 Gateway reconnect/resume는 discord.js가 담당한다. 3분 동안 회복되지 않는 연결은 재로그인을 시도한다. 한 프로세스에서 중복 로그인 시도와 중복 재시도 타이머를 방지하며 종료 시 모두 취소한다.

## 적용 전제와 한계

운영 앱이 보스 데이터를 변경하는 **단일 활성 인스턴스**인 구성을 전제로 한다. 같은 프로세스에서 발생한 컷/멍은 커밋 즉시 캐시에 반영된다. 다른 프로세스나 SQL 도구가 직접 변경하면 캐시 화면과 스케줄러 반영이 최대 10분 늦어질 수 있다. 다중 writer 환경에서는 분산 무효화 설계가 추가로 필요하며, 이 변경만으로 그 환경에서 알림 무누락을 보장하지 않는다. 향후 배포 시 기존/신규 운영 봇이 장시간 겹치지 않도록 확인해야 한다.

영구 원본은 PostgreSQL이고 메모리 캐시는 원본을 대신하지 않는다. 프로세스 재시작 후 DB에서 다시 읽는다. 새벽 절전 중 발생한 오래된 알림을 한꺼번에 보내지 않는 기존 90초 만료 정책은 유지한다. 따라서 서버가 꺼져 있던 시각의 정시 알림은 보장하지 않는다. Discord 전송 직후 DB 커밋 전에 프로세스가 죽으면 동일 알림이 재전송될 수 있는 기존 at-least-once 한계도 남아 있다.

## 검증 환경

- 로컬 Node 자동 테스트: 37개 중 36개 통과, 외부 PostgreSQL 전용 1개는 로컬에서 미실행. 실제 PostgreSQL 16 서비스로 실행하는 CI에서는 `TEST_DATABASE_URL`을 필수로 요구한다. CI의 최종 결과는 PR의 Checks에서 확인한다.
- 추가 SQL 검증: PGlite 0.5.13의 내장 PostgreSQL 엔진을 별도 메모리/디스크 DB로 실행했다. 운영 Neon 또는 기존 검증 Neon DB가 아니다. PGlite는 검증 도구로만 설치했고 앱의 runtime/package 의존성에 추가하지 않았다.
- Discord 재접속 시험은 가짜 토큰과 모의 Gateway 이벤트를 사용했다. 일시 실패 후 성공, 잘못된 토큰/intent, resume, 장기 단절, 로그인 시간 초과, 종료 후 재시도 금지를 확인했다. 실제 Discord 서버 연결/메시지 전송 시험은 하지 않았다.
- 디스크 SQL DB에 컷·멍을 기록하고 엔진을 완전히 닫았다가 재개했을 때 상태·이력·백업이 보존됨을 확인했다. 실패한 트랜잭션은 롤백됐고 캐시에 성공 기록을 남기지 않았다.
- 동일 시각에 여러 캐시 갱신 요청이 발생해도 갱신 SELECT는 하나만 실행되는지 확인했다. 화면·상태 검사·스케줄러가 같은 캐시를 사용하는지 확인했다.

## 17시간 기존 코드 대비 SQL 비교

가상 시계로 07:00~24:00에 해당하는 17시간을 실행했다. 30초마다 일정 타이머/상태 검사/화면 조회, 10초마다 Discord 대기열 처리를 실행했다. 기준 코드의 Store/Service는 운영 기준 commit에서 추출했고 개선 코드는 이 브랜치를 사용했다. 초기화 쿼리는 제외했다. 실제 HTTP 사용자 수나 실제 Neon 부하를 측정한 수치가 아니다.

| 시나리오 | 기존 SQL 호출 | 개선 후 | 감소 | 알림 검증 |
|---|---:|---:|---:|---|
| 예정 보스가 없는 대기 상태 | 28,561 | 101 | 99.65% | 양쪽 모두 알림 0개 |
| 31종 보스 예정·자동 넘김 | 32,736 | 4,357 | 86.69% | 알림 513개 및 자동 넘김 165개, 누락·추가 중복·전송 시각 차이 0개 |

두 실행의 보스 상태·멍 횟수·이력·대기열·중복 방지 키가 일치했다. 없는 `alarmKeys`와 빈 배열은 동등한 초기 상태로 정규화해 비교했다. 모의 전송 대상에 기록한 678개 이벤트의 ID·내용·순서·전송 시각도 일치했다. 별도 경계 시험에서 31종의 첫 10/5/0분 알림 93개가 모두 정확히 한 번 생성됐고 30분 자동 넘김도 일치했다. 이것은 **합성 시험의 결과**이며 실제 Discord 수신 무누락을 인증한 결과가 아니다.

세부 수치는 `free-uptime-query-comparison.json`에 있다.

## Neon 무료 사용량 해석

쿼리 수 감소율과 CU-hours 감소율은 같지 않다. 쿼리마다 5분의 활성 구간을 가정한 단순 모델에서, 대기는 17시간 중 약 8.5시간, 보스 31종 활성 시나리오는 약 13.9시간 DB가 활성 상태였다. 최소 0.25 CU와 31일을 가정하면 각각 약 65.9 / 107.7 CU-hours다. 실제 autoscaling, 대기 시간, 사용자 입력, Neon 내부 측정에 따라 달라진다.

따라서 대기 시 절감 효과는 확인했지만, 보스가 많이 등록되고 지속적으로 조작되는 상황에서 **월 100 CU-hours 이하를 보장할 수 없다**. Neon 실제 운영 프로젝트의 월 CU-hours 절감은 아직 측정하지 않았다. 무료 한도 초과 시 DB가 일시 중지될 수 있으므로, 향후 적용 여부는 이 한계를 포함해 판단해야 한다. 쿼리를 줄이기 위해 컷/멍 저장을 늦추거나 알림을 묶어서 지연 전송하지 않았다.

## 운영 적용 전 남은 확인

1. PR CI의 실제 PostgreSQL 동시성·롤백 검사 성공 확인.
2. 단일 활성 운영 봇 원칙과 기존/신규 버전 중복 실행 방지 확인.
3. 사용자가 원할 경우 별도 토큰·전용 채널에서 실제 Discord 수신 검증. 기존 운영 토큰으로 두 봇을 동시에 실행하지 않는다.
4. 운영 데이터·환경변수 최신 백업과 기존 버전 롤백 경로 확인.
5. 사용자 별도 승인 후에만 main 병합과 운영 배포. 이번 검증은 운영 반영 승인이 아니다.
